# 一页游戏设计文档（One-page GDD）

> 使用方式：复制“可直接填写的空白结构”到新文件或直接替换其中的方括号。所有内容保持通用、简短且可验证；不要在模板仓库中填入具体项目内容。

## 目的

用一页左右的内容对齐“怎样用游戏设计回应已确认的玩家需求、玩家做什么、为什么有趣、怎样算验证成功”。GDD 负责设计解决方案，不替代 `00_PRODUCT_REQUIREMENTS.md` 中的需求发现与分析。

## 填写说明

1. 先确认 `00_PRODUCT_REQUIREMENTS.md` 已完成需求确认并允许进入设计阶段。
2. 在写代码前由设计、开发和测试共同填写。
3. 用玩家可观察到的行为描述设计，少用“好玩”“丰富”“有沉浸感”等无法验证的词。
4. 只写当前要验证的最小体验；未来设想放入“不在本轮范围”。
5. 每个功能至少关联一个需求编号或编号明确、可证伪的试玩假设。
6. 数值只写配置名称、初值和调节范围，实际值应集中在 `src/config`。
7. 不确定内容标记为“待确认”，同时写负责人和确认日期，不要用猜测补齐。
8. 素材必须说明来源和授权方式；原型优先使用几何图形、系统字体和可删除占位音效。

## 推荐问题

- 本方案具体回应 `00_PRODUCT_REQUIREMENTS.md` 中哪条已确认需求？
- 用一句话怎样让目标玩家理解这个游戏？
- 玩家在 10 秒内能看懂目标和第一次操作吗？
- 一局期望多长，玩家为什么愿意立即再来一局？
- 每轮最重要的选择是什么，选择之间有真实取舍吗？
- 游戏如何回应玩家的动作？成功、危险和失败是否容易分辨？
- 哪条规则是体验成立的必要条件？删掉哪项仍能验证核心假设？
- 难度来自决策、执行、记忆，还是随机性？随机是否可复现？
- 哪些内容明确不做，避免原型悄悄变成正式制作？
- 需要观察什么行为才能判定假设成立或不成立？
- 是否触及网络、账号、付费、广告、隐私或素材授权边界？若是，本模板默认不支持，应先停止并重新决策。

## 完成判定标准

- [ ] 新成员可在两分钟内说清目标玩家、玩家目标、核心循环和单局结束条件。
- [ ] 设计方案关联已确认的需求编号，且未用 GDD 代替需求分析。
- [ ] 至少有一个编号明确、可证伪且带阈值的试玩假设。
- [ ] 规则、表现、配置和平台职责没有混写。
- [ ] 必要功能与可删除内容边界清楚，不依赖“以后再补”才能试玩。
- [ ] 随机性说明固定种子和复现方式，或明确写“无随机性”。
- [ ] 输入、反馈、重启、成功和失败状态均有定义。
- [ ] 不含后端、数据库、登录、支付、广告、在线 AI API 或前端密钥需求。
- [ ] 素材来源可核验，未知项有负责人和确认日期。
- [ ] 文档与 `00_PRODUCT_REQUIREMENTS.md`、`02_MVP_SCOPE.md`、`03_CORE_LOOP.md` 没有冲突。
