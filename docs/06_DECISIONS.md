# 决策记录模板

> 本文档采用轻量 ADR（Architecture/Design Decision Record）方式。保留已发生的关键决策及其背景，避免后来只看到结果、不知道为什么。

## 目的

记录会影响架构、范围、测试、玩家体验、安全或维护成本的重要取舍，包括备选方案、证据、后果和回滚条件。它帮助团队在新证据出现时有意识地替换旧决策，而不是反复争论或悄悄改变方向。

## 填写说明

1. 只记录难以撤销、跨模块或未来容易被质疑的决定；普通实现细节留在代码和 Pull Request。
2. 决策前创建“提议中”记录，列出至少一个现实替代方案和“不做”的结果。
3. 状态只使用：`提议中`、`已接受`、`已否决`、`已取代`、`已弃用`。
4. 已接受记录保持追加式历史，不静默改写原因。新证据推翻旧决定时，新建记录并互相链接。
5. 将玩家体验决定关联到试玩假设与证据，将技术决定关联到测试、包体、安全和回滚。
6. 依赖变化必须写明现有工具为何不足、稳定版本、维护者、许可证、包体和替代方案。
7. 未知内容写“待确认”，附负责人和日期。
8. 若用户需求、GDD、MVP、当前任务和既有决定冲突，停止实施并记录冲突，等待负责人选择。

## 推荐问题

- 现在必须做决定吗？推迟决定的成本是什么？
- 哪些约束来自用户、平台、安全、性能、授权或维护能力？
- 至少有哪些可行方案？“保持现状”是否也是方案？
- 哪个证据支持选择，哪个关键假设仍未验证？
- 对 `src/core` 纯净性、确定性、配置化和平台隔离有什么影响？
- 是否引入依赖、联网、密钥、个人数据或素材授权风险？
- 选择会增加多少包体、复杂度、测试面和长期维护负担？
- 什么信号会触发复审？如何以最低成本回滚？
- 哪些文档、测试、任务或使用说明必须同步更新？
- 谁拥有最终决定权，何时生效？

## 完成判定标准

- [ ] 决策索引与详细记录的 ID、状态和链接一致。
- [ ] 背景说明为什么现在需要决定，并区分事实与假设。
- [ ] 至少比较一个现实替代方案和“保持现状/不做”。
- [ ] 最终选择由证据与约束支持，不只记录结论。
- [ ] 玩家体验、核心架构、确定性、配置、平台、安全和维护影响已评估。
- [ ] 依赖决定包含稳定版本、必要性、替代方案、许可证、包体和维护风险。
- [ ] 正负后果、验证方式、复审触发条件和回滚路径明确。
- [ ] 受影响的设计、范围、试玩、指标、任务、代码和测试均列入同步清单。
- [ ] 旧决定未被静默改写；取代关系通过新记录追踪。
- [ ] 仍有冲突或待确认项时，明确负责人和日期，实施保持暂停。
