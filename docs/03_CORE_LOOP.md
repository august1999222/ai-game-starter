# 核心循环模板

> 核心循环描述玩家反复经历的“观察—决定—行动—反馈—新局面”。本文档同时把规则层和表现层分开，便于用固定输入稳定测试。

## 目的

明确每次玩家操作前后发生什么、状态如何转换、反馈何时出现，以及循环怎样结束并重新开始。它帮助开发者把可测试的规则留在 `src/core`，让 Phaser 只承担输入和表现。

## 填写说明

1. 先画最短的一轮循环，再描述整局如何由多轮组成。
2. 每一步都写玩家看到什么、可以做什么、核心状态怎样变化。
3. 规则使用普通数据和纯函数表达；不得引用 Phaser、DOM、时间或浏览器 API。
4. 所有数值、关卡数据和开关写成 `src/config` 键，不在流程里埋常量。
5. 随机分支必须说明何时消耗随机数、如何传递种子以及如何复现。
6. 动画可以延后显示结果，但不能决定规则结果。
7. 明确连续输入、无效输入、页面失焦、结束状态和重启的处理。
8. 将循环的关键选择关联到试玩假设和可观察指标。

## 推荐问题

- 玩家每轮先观察到哪些足以做决定的信息？
- 玩家有哪些动作，动作的成本和不可逆后果是什么？
- 核心状态在动作前后具体怎样变化？
- 即时反馈、延迟反馈和整局反馈分别是什么？
- 什么让下一轮局面与上一轮不同？
- 玩家何时成功、失败或主动退出？结束后怎样重启？
- 在动画尚未结束时再次输入会发生什么？
- 随机性改变的是选项、结果还是表现？能否用同一种子重放？
- Phaser 场景是否只翻译输入和显示核心结果？
- 哪个可观察行为能证明循环的关键选择被理解？

### 纯核心接口草案

```ts
type GameState = {
  // [只包含可序列化的规则状态]
};

type GameAction =
  { type: '[ACTION_NAME]' /* [普通数据] */ } | { type: 'RESTART'; seed: number };

type GameEvent = { type: '[DOMAIN_EVENT]' /* [供表现层读取的数据] */ };

type TransitionResult = {
  state: GameState;
  events: GameEvent[];
};

// 相同 state、action、config 与随机数状态必须返回相同结果。
function transition(
  state: GameState,
  action: GameAction,
  config: GameConfig,
): TransitionResult;
```

实际项目可调整类型名称，但必须保持核心层不依赖 Phaser、DOM 和浏览器 API。

### Phaser 与核心层边界

| Phaser/输入层负责                     | `src/core` 负责            |
| ------------------------------------- | -------------------------- |
| 将点击、触摸或键盘翻译为 `GameAction` | 验证动作是否合法           |
| 调用 `transition` 并保存返回状态      | 计算位置、计分、胜负和进程 |
| 根据状态和事件更新可见对象            | 生成确定性的领域事件       |
| 播放动画、粒子、音效                  | 定义重启后的完整规则状态   |
| 暴露稳定页面测试接口                  | 保证相同输入得到相同结果   |

## 完成判定标准

- [ ] 新成员可沿循环图解释一轮和一局，不需要查看场景源码。
- [ ] 每个玩家动作都有前置条件、状态变化、反馈和无效处理。
- [ ] 成功、失败、结算和重启形成闭环。
- [ ] 核心接口只使用普通数据，不依赖 Phaser、DOM 或浏览器 API。
- [ ] 配置键集中且有合法范围，场景中不需要写规则常量。
- [ ] 随机消耗与种子策略明确，可用版本、配置、种子和动作序列复现。
- [ ] 动画和输入时序不会改变规则结果。
- [ ] 核心循环每个关键路径都有对应的 Vitest 或 Playwright 验证。
- [ ] 至少一个循环行为直接对应可证伪的试玩假设。
- [ ] 与 GDD、MVP 范围和当前任务一致。
