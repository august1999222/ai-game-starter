# 产品需求与机会定义模板

> 使用方式：从模板创建具体游戏仓库后，再复制或直接填写“可直接填写的空白结构”。模板仓库只保留占位内容；未经确认的判断、指标和结论一律标记为“待验证”。

## 目的

在游戏设计与正式功能开发前，对齐项目机会、目标玩家、真实需求、约束和验证门槛。本文档回答“为什么做、为谁做、需要满足什么”，为一页 GDD 提供需求依据；它不负责定义具体玩法或表现方案。

## 填写说明

1. 先记录观察、访谈、试玩、公开数据等可核验信息，再写判断；事实与假设分开。
2. 不确定内容写“待确认”，并注明负责人、验证方法和日期，不要用猜测补齐。
3. 需求统一使用 `MUST-001`、`SHOULD-001`、`COULD-001`、`WONT-001` 格式编号；编号创建后不复用。
4. `MUST` 是首版必须满足，`SHOULD` 是验证后考虑，`COULD` 是以后可能加入，`WON'T` 是本阶段明确不做。
5. 每条需求必须写清用户价值、可观察验收标准、证据或来源和当前状态。
6. 成功、调整和停止门槛只能写为“待验证目标”；完成调研或试玩后再补充实际结果及来源。
7. 需求确认前可以做低成本调研或技术探针，但不得进入正式游戏功能开发。
8. 需求发生变化时保留原编号和变更记录，并同步检查 GDD、MVP、试玩计划与当前任务。

## 推荐问题

- 这是玩家真实存在的问题，还是团队未经验证的偏好？
- 为什么现在值得验证？不做或晚做的影响是什么？
- 哪些证据直接来自目标玩家，哪些只是推测？
- 谁最可能需要这类体验，谁明确不在本阶段服务范围内？
- 玩家会在什么设备、时长、姿势、网络和注意力条件下使用？
- 玩家当前怎样满足该需求，替代方案在哪些情境下仍然足够好？
- 第一版只需要证明哪一项核心价值？最低成本的反证方式是什么？
- 平台、性能、包体、人员、时间、预算、隐私、版权与合规约束是否真实可执行？
- 哪些结果应让项目继续、调整或停止？证据不足时是否保持“待验证”？
- 是否仍有未决问题足以阻止进入游戏设计阶段？

## 完成判定标准

- [ ] 项目机会说明了问题、现在验证的理由，并区分证据与假设。
- [ ] 核心用户、相关特征和非目标用户均有明确边界及依据。
- [ ] 时间、地点、状态、设备、时长、手势姿态和网络场景均已填写或标记待确认。
- [ ] 玩家需求包含期望体验、替代方案、未满足之处和可追溯证据。
- [ ] 玩家目标、项目目标和第一版唯一核心价值相互一致。
- [ ] 平台、屏幕、性能、包体、网络、时间、人员、预算、隐私、版权与合规约束均已评估。
- [ ] 所有需求使用统一编号，并具备用户价值、验收标准、证据来源和状态。
- [ ] 每个关键假设都有可能错误的原因、最低成本验证、通过标准和失败处理。
- [ ] 继续、修改和停止标准均在验证前定义，未验证指标没有被写成事实。
- [ ] 未决问题有负责人、验证方式、截止日期和状态，且没有遗漏会阻塞设计的问题。
- [ ] 当前版本、日期、决策人和是否允许进入设计阶段已明确记录。
- [ ] 若需求尚未确认，正式游戏设计与功能开发保持暂停。
