# MVP 范围模板

> MVP 是“能验证最重要试玩假设的最小版本”，不是功能很多但不完整的正式游戏。复制空白结构后填写；模板仓库保持内容通用。

## 目的

把想法切成一个可构建、可试玩、可判定的最小范围，明确本轮必须做、明确不做和优先删除的内容，防止开发过程持续扩张。

## 填写说明

1. 先确认 `00_PRODUCT_REQUIREMENTS.md` 中的需求已允许进入设计阶段，再从 `01_ONE_PAGE_GDD.md` 选择本轮唯一的主要试玩假设。
2. 每个 MVP 功能必须关联需求编号和待验证假设，并说明它如何帮助验证；无法关联就移到“不在范围”。
3. “必须有”只保留没有它就无法完成试玩任务的内容。
4. 用可观察结果写验收标准，并为每项标记自动测试或人工试玩方式。
5. 将数值、关卡数据和开关指向 `src/config` 中的计划配置键。
6. 把规则实现标记为 `src/core`，把输入和显示标记为 Phaser 层，平台能力标记为 `src/platform`。
7. 范围变化先修改本文档并记录原因，再改代码。
8. 时间不足时按照“删减顺序”删除，不能通过跳过测试来赶进度。

## 推荐问题

- 如果只能验证一个问题，本轮最想知道什么？
- 玩家完成一次核心循环最少需要哪些状态、动作和反馈？
- 哪项功能只是看起来完整，却不影响假设结论？
- 成功、失败、重启和异常输入是否都有最小处理？
- 哪些规则可以用纯 TypeScript 测试，哪些交互必须在浏览器验证？
- 范围中的每个数值是否都有配置入口和合理边界？
- 最差情况下先删什么，仍能得到有意义的试玩结论？
- 什么结果会让团队停止、调整或放弃这个方向？
- 是否有任何条目引入新依赖、联网、账号、支付、广告或未授权素材？

## 完成判定标准

- [ ] 只有一个主要试玩假设，且有通过、失败和后续决策阈值。
- [ ] 每个 MVP 功能都同时关联需求编号和待验证假设。
- [ ] Must、Should 和 Could 中引用的需求与假设可在需求文档和 GDD 中找到且保持一致。
- [ ] 每个 Must 条目都直接服务该假设，并有可观察验收标准。
- [ ] “明确不做”和删减顺序足以处理常见范围争议。
- [ ] 核心规则、Phaser 表现、配置和平台能力的边界明确。
- [ ] 初始、成功、失败、无效输入和重启状态均已定义。
- [ ] 单元、集成、端到端和真人试玩验证均有对应范围。
- [ ] 质量门槛不会因时间不足被跳过。
- [ ] 范围不要求后端、数据库、登录、支付、广告、在线 AI API 或前端密钥。
- [ ] 与 `00_PRODUCT_REQUIREMENTS.md`、`01_ONE_PAGE_GDD.md`、`03_CORE_LOOP.md` 和 `TASK.md` 一致。
